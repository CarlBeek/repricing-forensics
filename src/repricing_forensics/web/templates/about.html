About this analysis

What is EIP-8037?

EIP-8037 introduces native state creation gas: new state is charged by a static cost per state byte (CPSB), currently 1530 gas per byte in the research branch. The replay uses revm's native Amsterdam/EIP-8037 accounting path, including state gas, the per-transaction reservoir, EIP-7702 authorization effects, and EIP-7623 floor gas.

This analysis records whether a transaction still fits its original gas limit, the minimum gas-limit multiplier needed when it does not, state gas spent, initial reservoir size, runtime state gas, spillover beyond the reservoir, and baseline vs schedule refund details.

What is EIP-7904?

EIP-7904 proposes raising the gas cost of eight EVM opcodes whose prices have not been updated since Ethereum's Frontier release in 2015. Over that time, improvements to EVM interpreters have shifted the relative cost profile of instructions, but the gas schedule has not kept pace. Opcodes like DIV, SDIV, MOD, SMOD, ADDMOD, MULMOD, EXP, and KECCAK256 now consume more real CPU time per unit of gas than their peers, creating a potential vector for denial-of-service attacks that exploit the mispricing.

The proposed changes also adjust precompile costs to keep them consistent with the repriced opcode schedule. The full specification is available in EIP-7904.

How we measure impact

We forked reth and modified its EVM gas table to reflect each proposed schedule. The fork re-executes historical mainnet blocks exactly as they originally ran -- same state, same transaction ordering, same block headers -- but charges the new gas prices. For each transaction, the producer runs the baseline execution, then replays the schedule against the same pre-transaction state. The dashboard treats that producer classification as the source of truth.

Re-execution happens at the EVM level, not via tracing. The modified node processes each opcode natively, so the measurements capture the actual gas accounting path rather than an after-the-fact estimate.

What the data captures

Every replayed transaction is assigned exactly one impact bucket. All bucket counts are stored in block_coverage; only the drill-in buckets keep full per-transaction rows in divergences.

For drill-in rows, the analysis records:

  • Baseline gas used -- gas consumed under the current schedule.
  • Schedule gas used -- gas consumed under the active repricing schedule.
  • Status change -- whether the transaction flips from success to revert (or vice versa).
  • Divergence location -- the program counter and call depth where execution first diverges.
  • Call stack snapshot -- the full call chain at the point of divergence, including contract addresses and function selectors.
  • Per-opcode deltas -- how many additional gas units each repriced opcode contributes in the affected transaction.

How transaction divergences are classified

A transaction is counted as divergent when its bucket is anything other than unchanged. The classifier compares the baseline and schedule replay along these signals: final success status, gas used, emitted event logs, call-tree structure, return output, created contract address, and log bloom. The classifier then applies a fixed priority order so the most actionable signal wins.

  1. Schedule broke a successful transaction. If baseline succeeded and the schedule fails, the transaction enters the failure branch. This branch decides between wallet_fixable_shallow, wallet_fixable_deep_chain, aa_gas_reestimation, inconclusive_needs_higher_sweep, and contract_broken.
  2. Schedule rescued a failed transaction. If baseline failed and the schedule succeeds, the transaction is schedule_rescued. It is a finding, not a breakage count.
  3. Event logs changed. With no status flip, different logs classify as event_logs_changed, even if gas also changed.
  4. Gas changed. With the same status and same logs, any nonzero schedule_gas_used - baseline_gas_used classifies as gas_only.
  5. Only trace-level observables changed. If gas, status, and logs match, but the call tree, output, created address, or log bloom differs, the bucket is trace_only.
  6. Nothing changed. If none of those signals differ, the bucket is unchanged.

Bucket criteria

  • unchanged -- status, gas, logs, and trace-level observables all match baseline.
  • trace_only -- status, event logs, and gas match, but the call tree, output, created address, or log bloom differs.
  • gas_only -- status and event logs match, but schedule gas used differs from baseline gas used.
  • event_logs_changed -- status matches, but emitted logs differ. This keeps a full drill-in row.
  • schedule_rescued -- baseline failed and the schedule succeeds.
  • wallet_fixable_shallow -- baseline succeeded, the schedule fails under the original gas limit, and either a higher outer gas limit proves the original limit was the only issue or the OOG is attributed to the root frame.
  • wallet_fixable_deep_chain -- baseline succeeded, the schedule fails, the OOG is deeper than the root frame, and every parent-to-child hop on the OOG path forwarded proportional EIP-150 gas.
  • inconclusive_needs_higher_sweep -- baseline succeeded, the schedule still halts OOG at the highest configured gas-limit multiplier, and no fixed-gas bottleneck was proven. This keeps a drill-in row so the run can be repeated with a higher sweep ceiling.
  • contract_broken -- baseline succeeded, the schedule fails, and the failure is not wallet-fixable, not account-abstraction gas re-estimation, and not merely sweep-limited. This keeps a full drill-in row.
  • aa_gas_reestimation -- baseline succeeded, the schedule fails on a known ERC-4337 EntryPoint transaction, and the failure is OOG-class. The fix is re-estimating and re-signing the UserOp gas limits off-chain, not changing contract code.

Wallet-fixable vs contract-broken

Not all schedule-induced failures represent real contract breakage. If a transaction runs out of gas only because the outer transaction gas limit was too low, a wallet can fix it by raising the estimate and resubmitting. These transactions are wallet-fixable.

The producer checks this by walking the path from the root call to the out-of-gas frame. If every parent-to-child hop forwarded gas through the EIP-150 63/64 cap, raising the outer gas limit can propagate down the whole path, so the transaction is wallet-fixable even when the OOG is deep in the call tree.

Contract-broken transactions have a structural bottleneck. The chain walk found a caller that throttled the callee with the 2300 stipend, a small fixed gas value, or a fractional gas pattern below the 63/64 cap. A wallet cannot fix that by increasing the outer gas limit because the contract itself limits the sub-call. Fixing these usually requires a contract upgrade or migration.

The SSTORE refund complication

EVM gas accounting distinguishes between pre-refund and post-refund gas usage. SSTORE operations that clear storage slots earn a gas refund, but this refund is applied after execution completes. When a transaction runs out of gas under the new schedule, no refund is issued (the transaction reverted), so the reported gas_used can be dramatically higher than the baseline -- not because the opcodes cost that much more, but because the refund that would have offset the cost was never applied.

This means the raw gas delta for OOG transactions inflates the apparent cost increase. The analysis reports both the gross delta and the pre-refund headroom to give a more accurate picture.

The 63/64 rule and deep call chains

When a contract makes an external call, EIP-150 requires it to withhold 1/64 of available gas (the "63/64 rule"). The callee receives at most 63/64 of the caller's remaining gas. In deep call chains this compounds: each level withholds a fraction, and by depth 10 or more, a significant share of the original gas has been retained across the stack.

Under higher opcode prices, the compounding effect is amplified. Contracts that forwarded gas via CALL without specifying an explicit limit relied on the 63/64 share being "enough." When per-opcode costs rise, the same 63/64 share may no longer cover the callee's execution. Contracts that hardcode a specific gas stipend (e.g., 2300 for the transfer stipend) are especially fragile because the stipend was sized for the original gas schedule.

Limitations

  • Identical state assumption. Re-execution replays transactions against the same state that existed when they originally ran. In practice, if gas costs change, earlier transactions in a block may produce different state, which could alter the outcome of later transactions. This second-order effect is not captured.
  • Heuristic classification. The wallet-fixable vs contract-broken distinction relies on classifying gas forwarding as proportional, fixed, stipend, or fractional. Edge cases (for example, a contract that forwards gasleft() - 100) may be misclassified.
  • Labeling coverage. Contract and project labels come from public sources (Etherscan, 4byte directory). Unlabeled contracts appear by address only.
  • Sample, not census. The analysis covers a specific range of mainnet blocks. Contracts deployed after the sample period or rarely called within it may not appear in the results.
